## Task 2 预检暂停：token 计数器兼容性

- Context7 官方 LangChain API 文档说明 `ChatOpenAI.get_num_tokens_from_messages` 只适用于其支持的 OpenAI chat model 名称。对照实装的 langchain-openai 1.6.5 源码后确认，非已支持模型名前缀会抛 `NotImplementedError`。
- 这会影响 Claude、DeepSeek、Ollama 使用 OpenAI 兼容端点时的 token 预算裁剪。依据用户要求，遇到固定技术栈的兼容性冲突应先停下询问；Task 2 的上下文裁剪尚未实现，等待用户指定可接受的计数策略。
- 用户选择：“A”——采用 `tiktoken` 的 `cl100k_base` 做跨提供商近似 token 计数，并明确记录这不是 Claude、DeepSeek 或 Ollama 的精确 tokenizer。已通过 Context7 查证 OpenAI `tiktoken` 的 `get_encoding("cl100k_base")` 和 `Encoding.encode(text)` 官方 API；将 `tiktoken==0.14.0` 加入依赖。
- 用户随后在本地配置 DeepSeek V4 Pro；四条标注 Prompt 样例真实评估通过：普通售后问题没有编造物流状态并请求必要物流信息；信息不足时追问；拒绝编造退款状态；缺失订单号时追问且不承诺已操作。密钥只由本地配置加载，没有输出。
- Task 2 完成：实现和 `python -m pytest -p no:cacheprovider tests -q`（11 passed）通过，提示词样例已由实际模型验证；采用 Context7 查证的 `tiktoken cl100k_base` 近似预算策略，限制已写入设计。

## Task 3 开始：对话流式 API 与售后结构化提取

- Context7 核对当前 FastAPI SSE API（`EventSourceResponse` / `ServerSentEvent`，POST 可用）和 LangChain `with_structured_output` 约束；用户禁止工具调用，因此售后提取选择 `method="json_mode"`，不使用 `function_calling`。DeepSeek 官方 API 支持 Chat Completions 的 `response_format: {"type":"json_object"}`，并要求 Prompt 明确 JSON 输出。
- 尚未实现 Task 3；先写 API 验收测试并确认 RED，再实现流式与结构化接口。若真实模型不支持该 JSON 模式，将按已确认固定选型与行为边界暂停询问。
- TDD RED：新增 `test_chat_api.py` 后，三个接口测试因尚无 `app.services` 失败，空消息路由返回 404，符合预期。首次实现 GREEN 暴露 `ChatPromptTemplate.invoke()` 返回 `ChatPromptValue`，不能直接交给裁剪器；改为 `.to_messages()` 后对话 API 测试 4 项通过。
- Task 3 实现：新增 `/api/chat/stream`，逐块发 `token`，成功结束发 `done` 与会话 ID；失败发稳定 `error`，仅生成完整后保存轮次。新增 `/api/after-sales/extract`，经 `with_structured_output(AfterSalesExtraction, method="json_mode")` 返回固定三字段 JSON；无工具/函数调用。
- 售后标注集 4/4 通过 DeepSeek V4 Pro：三字段齐全、订单号缺失、诉求不明、字段全缺失时均匹配预期，空字段为 JSON `null`。最终后端验证 `python -m pytest -p no:cacheprovider tests -q` → 18 passed；`python -m compileall -q app` → exit 0。
